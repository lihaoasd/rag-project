# 全文检索集成方案对比（选型文档）

> 版本: v1.3 | 日期: 2026-08-19 | 状态: 待评审（选型决策用，非实施计划）

## 1. 背景与现状

系统当前检索能力（`backend/core/vector_store.py` + `core/retrieval.py`）：

- **向量检索**：Milvus 稠密向量（IVF_FLAT，IP 相似度），`retrieval_method=vector`；
- **混合检索**：稠密 + Milvus 内置 BM25 稀疏（jieba 分词），RRF / Weighted 融合，`retrieval_method=hybrid`；
- **前端高亮**：仅 `SearchView.vue` 的 `highlightText()` 做简单子串正则高亮；
- **数据落点**：切片文本保存在 PostgreSQL `document_chunks.text_content`（另有 Milvus 副本），原始文件在 MinIO；
- **未实现需求**：F-16 关键词高亮（P1）、F-17 原文跳转（P2）；无独立关键词检索模式、无模糊/短语/同义词、无后端高亮、无文档级聚合分页。

**本文目的**：穷举"全文检索"可选方案并对比优缺点，供选型决策。确认方向后再另写实施计划。

## 3. 方案 A：扩展现有 Milvus 内置 BM25

### 做法

1. 新增独立 `keyword`（纯 BM25）检索方式，不再强制与稠密融合；
2. `BM25BuiltInFunction` 的 `analyzer_params` 增加自定义词典（`dict`），提升投标术语切分（"建筑工程施工总承包一级"等）；
3. 后端用 jieba 对 query 分词（与 Milvus 内置 jieba 分词结果基本一致），在命中文本中定位词位置，返回高亮片段/位置，替换前端简单子串高亮。

### 优点

- **零新增基础设施**，改动全部落在现有链路（schemas / retrieval.py / SearchView.vue）；
- 检索延迟低（本地 Milvus，无网络跳转）；
- 与稠密向量**天然 RRF 融合**（hybrid 已是现状），问答链路无缝受益；
- 无需同步管道：索引写入、删除、重建沿用 `build_index()` / `delete_index()`。

### 缺点

- **词袋模型**：无布尔（AND/OR）、短语、前缀、通配、模糊、同义词能力；
- **高亮需自建**：Milvus 不返回命中位置，需自己分词 + 定位，与 Milvus 实际分词存在偏差风险；
- **词典固化在建 Collection 时**：调整词典需删除重建 Collection（数据重灌），迭代成本高；
- **查询时实时计算 BM25**：文本量增大后查询开销上升（相对倒排索引）；
- **分数不可解释**：RRF/BM25 分数不是 [0,1] 相似度，无调试/Explain 工具；
- 无分页、聚合、过滤语法（只有标量字段过滤）。

### 成本与风险

- 开发量：小（数日）；风险：中低。
- 依赖验证点：llama-index/pymilvus 对**纯稀疏查询模式**（`VectorStoreQueryMode.SPARSE`）在 `MilvusVectorStore` 的支持程度（Milvus 服务端本身支持纯稀疏查询）。

### 适用场景

- 目标仅是"关键词能搜到 + 高亮"，且不想引入任何新组件；作为 RAG 检索的召回增强。

## 4. 方案 B：PostgreSQL 全文检索

数据切片**已在 PG**，这是本方案的最大优势：无需任何同步管道。

### B1：PG 原生 FTS（zhparser / pg_jieba + GIN tsvector 索引）

#### 做法

1. `document_chunks` 增加 `tsvector` 生成列（或触发器维护），建 GIN 索引；
2. 查询用 `to_tsquery / plainto_tsquery / websearch_to_tsquery`（支持布尔、短语、前缀）；
3. 排序用 `ts_rank / ts_rank_cd`；高亮用 `ts_headline()`；
4. 分词扩展二选一：
   - **zhparser**：SCWS 词库，PG 中文 FTS 事实标准；
   - **pg_jieba**：jieba 的 PG 移植，与现有 Milvus 分词一致（跨源分词一致性更好）。

#### 优点

- **真倒排索引，精确匹配**：命中即命中，语义确定、可解释；
- 布尔 / 短语 / 前缀查询原生支持；
- **`ts_headline()` 原生高亮**，无需自建定位逻辑；
- **SQL 直查**：过滤（kb / doc / file_type / 页码）、分页、聚合全部白拿；
- 事务一致性：与 `document_chunks` 同库同事务；
- 与 Milvus 向量分数可在 Python 端归一化后 **RRF 融合**；
- 无需新服务，索引维护（reindex）与备份走 PG 既有能力。

#### 缺点

- **扩展需编译安装**：官方 `postgres:16` 镜像不含 zhparser/pg_jieba，需自建 Dockerfile（build-essential + pgxs + 源码编译）或使用社区镜像；
- 中文分词质量取决于扩展词库：SCWS/jieba 通用词库对**投标专业术语**仍需自定义词典；
- 分词配置变更需重建 tsvector 索引（reindex，量级大时耗时）；
- PG FTS 是"关键词检索"，无向量语义；
- 单一 PG 实例的规模上限（本项目量级绰绰有余）。

#### 成本与风险

- 开发量：中（镜像改造 + Alembic 迁移 + repository 新查询 + 服务层融合）；风险：中。
- 主要风险：Docker 扩展构建在离线/受限网络下耗时；zhparser 对超短查询（1~2 字）排序噪音大。

### B2：pg_trgm（无需分词，GIN trigram 索引）

#### 做法

1. `CREATE EXTENSION pg_trgm;`（官方镜像自带，零镜像改造）；
2. `text_content` 建 `GIN (text_content gin_trgm_ops)` 索引；
3. 查询 `ILIKE '%关键词%'` / `ILIKE '前缀%'` 走 trigram 索引；`similarity()` / `%` 运算符做近似（容错）匹配。

#### 优点

- **零依赖零镜像改造**：PG 16 自带 contrib，一条 SQL 启用；
- **中文无需分词**：按字符 ngram 匹配，子串命中直观，专业术语天然可命中（不必先切对词）；
- 支持前缀匹配与模糊容错（`similarity`），用户体验直接；
- 与 SQL 生态无缝，适合"文档内检索 / 定位跳转"场景。

#### 缺点

- **无词义概念**：只是子串/字符相似度，没有 tf-idf 式相关排序，结果排序质量弱于 FTS/BM25；
- 索引体积约为文本的 1~2 倍；
- 短查询（<3 字符）无法走索引（需 pad 处理），长文本 bigram 噪音多；
- 无布尔/短语语法。

#### 成本与风险

- 开发量：小-中；风险：低。
- 适用：作为模糊/容错补充，或"文档内检索"主方案；**不建议单独作为搜索页关键词检索主方案**。

### B3：LIKE/ILIKE 朴素查询（基线）

- 做法：`WHERE text_content ILIKE '%kw%'`，无索引全表扫描。
- 优点：零成本、零依赖、几行代码。
- 缺点：无索引慢（全表扫）、无排序、无分词。
- 定位：仅数据量极小时的兜底或原型，**不作为正式方案**，仅作对比基线。

## 5. 方案 C：专用全文检索引擎

共同点：新增独立服务 + **需要与 Milvus/PG 双写同步**（chunk 写入时推送或 CDC），引入一致性与运维成本。

### C1：Elasticsearch / OpenSearch

#### 做法

- 新增 ES/OpenSearch 集群；安装 **IK 中文分词插件**；chunk 文本随索引流程写入 ES（或 PG binlog CDC）；搜索 API 走 ES。

#### 优点

- **功能最全**：IK 分词、同义词、停用词、模糊、通配、短语、聚合、原生高亮、Explain、滚动分页、排序调优；
- 生态成熟，检索质量与调优能力是行业标杆；
- 分布式可横向扩展（海量数据场景）。

#### 缺点

- **JVM + 内存**（建议 ≥ 1~2GB，堆调优复杂）；
- **索引生命周期管理**：段合并、ILM、备份恢复、监控告警，运维成本最高；
- **双写一致性**：与 Milvus 同步的失败重试、补偿、对账机制要自建；
- 授权注意：ES 8.x 为 SSPL/Elastic License，OpenSearch 为 Apache 2.0；
- 对本项目（本地部署、文档量级有限）明显**过度设计**。

#### 成本与风险

- 开发量：高；风险：高（运维 + 一致性）。
- 适用：上万文档、多人团队、对检索体验/聚合分析有硬要求时才值得。

### C2：Meilisearch

#### 做法

- 单 Rust 二进制 + 索引目录；HTTP API 推送 chunk 文本；搜索/高亮/容错开箱即用。

#### 优点

- **部署极简**（单二进制，内存数百 MB）；API 简单；
- **开箱即用体验好**：错字容错（typo tolerance）、前缀搜索、原生高亮（`_formatted`）、facet 过滤；
- 相关排序默认质量不错，几乎免调参。

#### 缺点

- **中文分词一般**（charabia 对中文近似逐字/短 ngram，无 IK 级词库），投标专业术语检索质量可能不达预期；
- 同义词/自定义分词能力弱于 ES；
- 仍需与 Milvus/PG 的**同步管道**；
- 海量聚合/高并发能力不如 ES。

#### 成本与风险

- 开发量：中；风险：中（中文质量 + 同步）。
- 适用：想要"搜索框体验好"且接受新组件，但不需要 ES 级能力。

### C3：Typesense

#### 做法

- 单 C++ 二进制，mmap 内存友好；HTTP API；内置容错、高亮、facet、同义词。

#### 优点

- 轻量、快、部署简单；内存占用低；
- 原生高亮/容错/分面，开箱即用。

#### 缺点

- **中文分词弱**（默认逐字/ngram 级别）；
- 生态与扩展性小于 ES；
- 仍需同步管道。

#### 成本与风险

- 开发量：中；风险：中（中文质量 + 同步）。
- 适用：与 Meilisearch 类似，偏轻量自托管。

## 6. 方案 D：前端/客户端本地检索

### 做法

- 后端按 kb/doc 分页拉取切片文本，前端用 **fuse.js / minisearch**（内存索引）或纯 JS 过滤 + 正则高亮，实现即时搜索与定位跳转。

### 优点

- **零后端改动**、零基建；交互即时，无网络往返；
- 高亮/定位/跳转（配合 F-17 原文跳转）实现最简单直接；
- 适合"**文档查看器内单文档检索**"场景。

### 缺点

- 数据全量拉到浏览器：大文档/多文档时**内存与流量**不可控；
- 分词与相关性弱，无法做跨库大规模语义检索；
- 刷新即丢索引（每次重拉）。

### 成本与风险

- 开发量：小；风险：低。
- 定位：单文档内检索或原型验证；**不替代**后端检索。

## 7. 方案 E：多路召回组合（演进形态）

### 做法

- 关键词路（A 的独立 BM25，或 B1/B2 的 PG FTS）+ 向量路（Milvus 稠密或 hybrid）→ Python 端归一化后 **RRF 融合** →（可选）rerank 模型收口。

### 优点

- **兼得**精确关键词命中 + 语义召回，搜索页与 RAG 问答质量同时提升；
- **渐进式**：先 A 后 B，按需叠加，不必一步到位；
- 融合层与现有 `search_service.search()` 结构兼容（已是多路合并排序 + 可选 rerank）。

### 缺点

- 多一路召回 → 开发与调参（融合权重/阈值/归一化）成本；
- 两套分数体系并存，调试链路变长；
- 查询延迟为各路之和（并发可缓解）。

### 成本与风险

- 开发量：中（分阶段）；风险：中低。
- 定位：最终形态建议，具体组合取决于选型结论。

## 9. 检索效果对比

> 检索效果不能只靠方案特性下结论，但**各方案的效果特征是可以预期的**。以下是按效果维度的拆解，最终数字建议用评测集验证（见 9.4）。

### 9.1 效果维度

| 维度 | 含义 | 对投标场景的意义 |
|------|------|------------------|
| 精确术语召回 | 招标编号、资质名称（"建筑工程施工总承包一级"）、公司名、标准条款号这类**必须字面命中**的查询 | 精确实体是投标检索的高频诉求，关键词路 vs 向量路差距最大的一档 |
| 语义召回 | 换说法、自然语言描述（"有没有做过类似的市政项目"）也能命中 | 只有向量路 / hybrid 覆盖，纯关键词方案全灭 |
| 排序质量 | top-k 里相关结果是否靠前（MRR / NDCG / 人工看 top-5） | 直接决定用户和 RAG 问答看到的内容 |
| 中文分词与专业术语 | 通用词典切分不准时能否正确命中 | 术语切分错了，词袋检索就漏 |
| 高亮准确度 | 高亮片段是否精确落在命中词上 | F-16 需求，影响可读性 |
| 模糊容错 | 输入错字/简写/多词组合的容忍度 | 用户输入质量不可控时的兜底 |

### 9.2 各方案效果一览（含现状基准）

| 方案 | 精确术语召回 | 语义召回 | top-k 排序质量 | 中文专业术语 | 高亮准确度 | 模糊容错 |
|------|--------------|----------|----------------|--------------|------------|----------|
| 现状：vector（稠密） | ❌ 弱（专名不在语义近邻） | ✅ 强 | 语义查询好 / 关键词查询差 | 无关（不看词） | 前端子串，对不上语义命中 | ❌ |
| 现状：hybrid（稠密+BM25） | ✅ 中 | ✅ 强 | 融合后整体稳，个别 top-k 混噪音 | 中（jieba 通用词典） | 同 vector | ❌ |
| A：BM25 扩展（独立 keyword + 词典） | ✅ 中高（词典后提升） | ❌ 无 | BM25 排序可靠可解释 | 中（自定义词典提升） | 需自建，分词偏差风险 | ❌ |
| B1：PG FTS（zhparser/pg_jieba） | ✅ 高（布尔/短语加持） | ❌ 无 | ts_rank 中等，弱于 BM25 | 中（自定义词典提升） | ✅ ts_headline，按分词粒度 | 前缀/短语，无错字容错 |
| B2：pg_trgm | ✅ 高（子串天然命中，**无需切对词**） | ❌ 无 | 弱（无词义权重，长文本噪音） | ✅ 最强（切分不准也不漏） | 自建（子串定位简单可靠） | ✅ similarity 容错 |
| C1：ES/OpenSearch（IK） | ✅ 最高（IK+同义词+模糊+通配） | ✅ 可（ES 原生 kNN+BM25 RRF） | ✅ 最强可调（BM25 参数/boost） | ✅ 最强（IK+自定义词典+同义词） | ✅ 原生（match 高亮） | ✅ 全套 |
| C2：Meilisearch | ✅ 高（字面+容错） | 有限（新版有向量混合，生态弱） | ✅ 默认相关排序好 | 一般（charabia） | ✅ 原生 `_formatted` | ✅ 内置 typo |
| C3：Typesense | ✅ 高 | 有限（新版有向量混合） | ✅ 默认不错 | 弱 | ✅ 原生 | ✅ 内置 |
| D：前端本地（fuse.js） | ✅ 中（内存内子串/模糊） | ❌ | 弱-中 | 中（逐字） | ✅ 即时精确 | ✅ 内置容错 |

### 9.3 效果规律（关键结论）

1. **精确实体查询：关键词路碾压向量路**（BM25 / PG FTS / pg_trgm / IK 都好于稠密向量）。其中 **pg_trgm 因"无需分词"，对切分不准的专业术语反而最稳**——这正是投标文档的高频痛点。
2. **语义查询：只有向量 / hybrid 能覆盖**。纯关键词方案对"换说法"的查询召回为零，RAG 问答必须保留向量路。
3. **排序质量排序**：IK/BM25 系 > ts_rank > trigram > 前端逐字。但**最终 top-k 质量强烈依赖 rerank 模型**——现有链路已接 rerank，无论选哪一路召回，都建议保留 rerank 收口，它能抹平大部分排序差距。
4. **融合 > 单路**：RRF 融合（现状 hybrid 已是此形态）召回率稳定提升，代价是 top-k 可能混入单路噪音；用 rerank 过滤即可。
5. **高亮**：ES / ts_headline 原生且准确；Milvus 需自建且与检索侧分词存在不一致风险；前端正则只对字面子串有效（语义命中的结果高亮不上）。
6. **B1 与 A 的分词同源**（jieba）：术语问题一致，都靠自定义词典；若追求"不改分词就命中"，B2（trigram）比两者都稳。

### 9.4 效果评估方法（建议落地）

选型前先花半天建**投标领域评测集**，用数据说话：

1. **构建评测集**：20~50 条 query，覆盖 5 类——精确术语（资质/编号/公司名）、语义改写、模糊描述、多关键词组合、超短查询（≤3 字）；每条人工标注期望命中的 chunk 或文档。
2. **指标**：recall@k、precision@k、MRR（排序质量）、人工相关性打分 top-5。
3. **跑对比**：同一评测集上依次跑 `vector` / `hybrid`（现状可 A/B）/ 独立 BM25（A）/ PG FTS（B1）/ pg_trgm（B2），输出对比表。
4. **决定**：按对比结果定默认检索方式、融合权重、是否需要 rerank 兜底。
5. **成本**：脚本化评估半天到一天，远低于选错方案的重做成本。

### 9.5 效果维度结论

- 关键词检索效果"立竿见影"的优先级：**B2（术语召回最稳）≥ B1（排序更好）> A（与现状融合成本最低）**；
- 但 top-k 的最终体验由 **rerank 模型**决定，选型不该脱离现有 rerank 链路单独评判；
- 具体数字以评测集为准，**不建议仅凭方案特性拍板**。

## 10. 自建词库支持对比

> 需求前提：需要维护**自定义分词词典**（投标专业术语、资质名称、公司名、项目名等），确保检索时能正确切分与命中。本文档不依赖其他词库设计（docs/04 不作为约束），以下按"检索侧独立自定义词典"评估。

### 10.1 词库在检索侧的三层作用

| 层 | 作用 | 消费方 |
|----|------|--------|
| 分词词典 | 决定"词"能否被正确切出、检索到（专业术语切分） | BM25 / FTS 分词器 |
| 查询改写词典 | 同义词/别名 → 标准名（"甲建设集团"→"甲公司"），扩展 query 提升召回 | 查询预处理层 |
| 高亮词典 | 精确高亮命中的领域词 | 高亮实现 |

### 10.2 各方案对"自建词库"的支持

| 方案 | 分词词典支持 | 生效方式 | 更新成本 | 备注 |
|------|--------------|----------|----------|------|
| A：Milvus BM25（jieba） | ✅ `analyzer_params.dict`（JSON 自定义词典，见 [Zilliz/Milvus jieba tokenizer 自定义配置](https://docs.zilliz.com/ja-JP/docs/jieba-tokenizer#custom-configuration)） | **建 Collection 时固化** | **重建 Collection + 重灌全部数据（最贵）** | 关键坑：Python 侧 `jieba.add_word()` **不影响 Milvus 服务端分词**，两套 jieba 需分别维护 |
| B1：PG FTS（zhparser） | ✅ `zhparser.extra_dicts` / multi_* 模式 | 重载配置后生效 | **REINDEX tsvector 索引（不重灌数据）** | 与 Python jieba 仍是两套词典，需同步维护 |
| B1：PG FTS（pg_jieba） | ✅ 支持自定义词典（user.dict 机制，见 [yanyiwu/pg_jieba](https://github.com/yanyiwu/pg_jieba)） | 重载后生效 | REINDEX tsvector | 同上 |
| B2：pg_trgm | **不需要分词词典**（子串命中） | — | — | 词库仅用于查询改写/高亮增强（可选） |
| C1：ES + IK | ✅ main.dic + `remote_ext_dict` 远程词典 | **支持热更新** | 无索引重建，热加载 | 词库能力天花板（含同义词、停用词） |
| C2/C3：Meilisearch / Typesense | ❌ 基本不支持自定义中文词典 | — | — | 直接排除"自建词库"路线 |
| D：前端本地 | 词库做查询扩展/高亮，能力弱 | — | — | 不作为主方案 |

### 10.3 关键结论

1. **词库更新成本是选型第一要素**：Milvus BM25 改词典 = 重建 Collection + 重灌数据；PG FTS 改词典 = REINDEX（秒~分钟级，不重灌）；ES+IK 支持热更新。若词库会频繁迭代，Milvus BM25 的更新成本**不可接受**；低频维护则 A 也可接受。
2. **Python jieba ≠ Milvus 服务端 jieba**：在 Python 侧 `jieba.add_word()` 只影响 Python 进程（解析、查询预处理、高亮），不会改变 Milvus 服务端 BM25 分词。选方案 A 需额外把词库导出为 Milvus dict JSON 并在建 Collection 时传入，且无法热更新。
3. **一份词库、多端导出**：自定义词典建议单一来源（文件或 PG 表），做统一导出器同时生成：Python jieba 词典、Milvus dict JSON、zhparser/pg_jieba 词典、IK 词典、查询改写同义词表——避免多端手工维护漂移。
4. **想彻底绕开"分词切不准"**：B2（pg_trgm）无需词典也能命中专业术语，词库只承担查询改写（别名→标准名扩展）与高亮增强，职责单一、最省心。

### 10.4 词库维护建议（与引擎解耦）

- 词典单一来源（例如 `backend/lexicon/` 下的 TSV/JSON 文件，或 PG `terms` 表），按引擎格式导出分发；
- 更新入口统一（文件/管理接口），更新后按各端生效成本执行：Milvus 重建 Collection / PG REINDEX / IK 热更新；
- 若词库更新频繁，优先选"热更新或轻量重建"端（PG FTS / ES），回避 Milvus 重灌。

### 10.5 前端更新词库的实现形态（需求：通过前端界面维护词典）

| 方案 | 前端更新流程 | 生效成本 | 可行性 |
|------|--------------|----------|--------|
| A：Milvus BM25 | 前端 → 后端 → **重建 Collection + 重灌全部知识库数据** | 全量重灌（分钟~小时级），期间检索不可用 | ❌ **基本不可行**：每次改词库都全量重灌，交互式维护无法接受 |
| B1：PG FTS（zhparser/pg_jieba） | 前端 → 后端写词典文件（PG 容器挂载卷）→ 重载配置 → REINDEX | REINDEX（秒~分钟级）+ 配置重载 | ✅ 可行：后端异步任务完成，检索不中断；需改造 docker-compose 挂载词典目录 |
| B2：pg_trgm | 前端 → 后端写 PG `terms` 表 → 查询时实时读取（内存缓存刷新） | **零重建，即时生效** | ✅ **最简**：词典只是数据，与索引完全解耦 |
| C1：ES + IK | 前端 → 后端写词典 → IK `remote_ext_dict` 远程词典热加载 | 热更新，零重建 | ✅ 体验最优，但基建/双写最重 |
| C2/C3：Meilisearch / Typesense | 不支持自定义词典 | — | ❌ |

**结论**："前端更新词库"需求下：

1. **方案 A（Milvus BM25）被排除**——改词典 = 全量重灌，交互式前端更新不可行；
2. **方案 B2 最契合**——词典以 PG `terms` 表形式存在，前端 CRUD 后查询时实时生效，零重建、零镜像改造；
3. **方案 B1 次选**——排序质量更好，但前端更新要走"写词典文件 → 重载 → REINDEX"的后端异步任务，且需改 PG 镜像与挂载卷；
4. **方案 C1 体验最优**（IK 热更新），但基建成本与双写同步最重，仅在规模/词库迭代极高时评估。

## 11. 决策建议（按需求场景）

| 你的核心诉求 | 推荐方案 | 理由 |
|--------------|----------|------|
| 搜索页更精准的关键词检索 + 高亮，不想加组件 | **A**（独立 keyword 模式 + 投标词典 + 后端高亮） | 零基建、改动小；不足时叠加 B |
| 想要真倒排索引（布尔/短语/高亮/过滤分页） | **B1**（pg_jieba 优先，分词与现有 Milvus 一致） | 数据已在 PG，无同步；ts_headline 原生高亮 |
| 文档查看器内单文档全文检索/定位跳转 | **D** 或 **B2** | D 零后端改动；B2 可后端分页 + trigram 模糊 |
| 要求高级体验（模糊/同义词/聚合）且接受基建 | **C2/C3**（轻）→ **C1**（重） | 按资源与运维能力选择 |
| 长期演进 / RAG 问答质量优先 | **E**（先 A 后 B，RRF 融合 + rerank 收口） | 渐进式、风险可控 |
| **需要自建词库 + 前端更新** | **B2** 首选（词典=PG `terms` 表，前端 CRUD 即时生效，零重建零改造）；要更强排序选 **B1**（reload+REINDEX 异步任务）；**A（Milvus BM25）排除**（改词典=全量重灌） | 词典与索引解耦，前端维护即时生效 |

**个人倾向**：数据已在 PG，先做 **A**（最小改动满足"关键词+高亮"），随后按需叠加 **B2（pg_trgm 兜底模糊）→ B1（真 FTS）**，最终收敛到 **E** 形态。**C 系列仅在规模/需求明确升级后评估**。

> **补充（自建词库 + 前端更新前提下的修正）**：方案 A（Milvus BM25）因"改词典=全量重灌"被**排除**；推荐 **B2（pg_trgm）**——词典以 PG `terms` 表形式由前端维护，查询时实时生效，与索引完全解耦；若后续要更强排序质量，再叠加 **B1（PG FTS）**，词典更新走后端异步"写词典文件 → 重载 → REINDEX"。

## 12. 待确认问题（影响选型）

1. "全文检索"的核心场景是：搜索页关键词检索？文档内检索？还是 RAG 问答召回增强？（决定 A / B2+D / E）
2. 数据规模量级（文档数、切片数）？（决定是否需要 C 系列）
3. 是否接受新增基础设施（内存/运维）？（决定 A/B vs C）
4. 是否需要后端高亮、模糊容错、同义词等高级能力？（决定 A vs B1 vs C）
5. 是否接受改造 PG 镜像（编译 zhparser/pg_jieba 扩展）？（决定 B1 vs B2）
6. 词库更新频率？（前端维护已确认；高频迭代 → B2 即时生效 / B1 reload+REINDEX，回避 Milvus 重灌）
