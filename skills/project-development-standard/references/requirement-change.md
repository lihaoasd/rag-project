# 需求变更要求

本文件用于“改需求/增加功能/调整行为/改接口”任务。变更前先评估影响，不直接改代码。

## 1. 明确变更

- 确认新需求的内容、动机、优先级、影响范围和验收标准。
- 对比旧行为和新行为，列出必须改变与不能改变的部分。
- 有歧义时列出问题清单，先补齐设计再开发。

## 2. 影响分析

- 检查受影响文件、模块、接口、数据模型、数据库迁移、缓存、消息、配置、UI、文档和测试。
- 识别调用方、兼容性、安全/性能影响。
- 输出影响清单，作为方案评审输入。

## 3. 更新设计文档

- 先更新需求/技术方案/接口文档，再写代码；文档放入对应分类目录。
- 涉及破坏性变更时，明确迁移方案、废弃策略和兼容窗口。
- 边界条件、异常场景、输入输出必须写清楚。

## 4. 开发方案与实现

- 在 `docs/plan/` 写变更方案，包含改动范围、步骤、伪代码和验证方式。
- 按最小 diff 实现：只改需求要求的部分，不顺手优化无关代码。
- 保持已有公共契约稳定；契约必须变化时同步更新调用方和文档。

## 5. 测试与验证

- 为新增/变更行为补充测试；覆盖正常路径、边界、旧行为兼容性。
- 运行全量相关测试，确认回归可控。
- 验收新需求并检查是否遗留未更新文档、配置或迁移脚本。
- 在修改记录中写入变更动机、影响范围、兼容性处理和验证结果。

## 反模式

- 跳过影响分析直接搜索代码修改。
- 只改一处调用，不处理数据迁移或兼容性。
- 新需求实现后旧测试被删除而没有解释。
- 把无关重构混入需求变更。
