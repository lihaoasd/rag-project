# 代码质量标准

本文件定义“高扩展、高可读、高复用”和抽象边界要求。实现前先读本文件。

## 抽象边界

- 抽象只在能消除真实重复、稳定扩展点或显著降低调用方复杂度时引入。
- 不为“以后可能用到”的场景提前抽象；至少存在两个真实使用方或明确扩展需求时再评估。
- 每层只负责一个领域，依赖方向指向稳定抽象，避免跨层访问私有实现。
- 公开 API 是模块边界；内部实现可以替换，调用方不应依赖内部细节。

## 高扩展

- 新增功能优先通过组合、策略、接口或既有框架机制实现，尽量不修改核心流程。
- 扩展点必须由当前需求驱动，接口保持小而稳定，避免通用配置参数堆积。
- 修改数据模型或接口时优先向后兼容；破坏性变更必须显式说明并更新所有调用方。
- 不允许多个地方用分支链模拟同一多态行为；优先使用语言/框架既有模式。
- 扩展代码不能以牺牲可读性为代价；不引入“万能工厂”或“统一入口”。

## 高可读

- 命名表达意图：变量、函数、模块名应能直接解释行为，不依赖注释补全。
- 函数/方法职责单一；过长函数先拆成表达意图的子函数，但不为拆分而拆分。
- 控制流保持直白：减少多层嵌套，复杂条件先提取为命名清晰的布尔值或函数。
- 注释解释“为什么”和约束，不重复代码本身。
- 匹配项目既有命名、目录、错误处理和代码风格；新代码不创造并行风格。

## 高复用

- 相同行为只保留一份实现；发现重复时先确认是否可以抽取，再决定是否复用。
- 优先复用项目内公共模块、标准库和既有依赖，不重新实现已有能力。
- 现有实现与需求不完全匹配时，先评估小范围适配或组合，不直接复制后改参数。
- 通用逻辑放公共层，业务逻辑放业务层；不让业务代码依赖一次性私有实现。

## 反模式

- 为想象场景提前抽象：接口、配置项、扩展点没有真实使用方。
- 上帝对象/万能工具类：把不相关能力塞进一个模块。
- 复制粘贴后改参数：重复实现导致 bug 分叉。
- 用大量配置掩盖未理解的需求。
- 抽象层过深：调用链无法在合理篇幅内解释清楚。
