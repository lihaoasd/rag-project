# 文档分类要求

所有项目文档必须按类别存放，禁止把不同性质的文档堆在 `docs/` 根目录或散落在代码目录。

## 推荐目录

- `docs/requirements/`：需求文档、用户故事、验收标准
- `docs/design/`：技术设计、架构设计、数据库设计、接口设计、专项设计
- `docs/plan/`：开发方案、实施计划、排期与步骤
- `docs/changes/`：修改记录、变更日志、发布说明
- `docs/api/`：对外接口文档、API 约定、错误码
- `docs/frontend/`：前端风格、UI 规范、组件约定、交互与响应式要求
- `docs/operations/`：部署、运维、环境配置、迁移执行手册
- `docs/testing/`：测试计划、测试报告、验收记录

如果项目已有明确约定，优先沿用；没有约定时使用上述结构。

## 文件命名

- 分类由目录表达，不靠文件名编号堆叠；例如 `docs/design/03-database-design.md` 可整理为 `docs/design/database.md`。
- 文件名简短、语义明确，能说明文档类型和主题。
- 同一主题存在多个版本时，使用日期或版本号区分，避免 `final-final` 式命名。

## 文档职责

- 一个文档只承担一个主要职责；需求、设计、计划、记录、报告不要混在同一文件。
- 关联文档使用相对链接互相引用，不复制全文。
- 修改记录必须写入 `docs/changes/` 或既有 changes 约定，不能追加进设计文档。

## 文档变更

- 新建文档时先确认归属分类。
- 重命名或移动文档时同步更新所有引用。
- 文档过期时标记状态，不直接删除唯一资料，除非有明确要求。
- `docs/` 根目录只放索引/README；正式文档进入对应分类。
