# 核心底线标准

来源：项目根目录 `CLAUDE.md`。以下为不可省略的默认行为准则；本 skill 的流程必须与这些准则一致。

## 1. 先思考再编码

**不要假设。不要隐藏困惑。呈现权衡。**

实施前：
- 明确陈述你的假设。如果不确定，就问。
- 如果存在多种理解，把它们都列出来，不要默默选择一种。
- 如果有更简单的方案，说出来。必要时提出异议。
- 如果有不清楚的地方，停下来。说清楚哪里困惑。然后问。

## 2. 简洁优先

**用最少代码解决问题。不做投机性开发。**

- 不添加需求之外的功能。
- 不为一次性代码创建抽象层。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果你写了 200 行代码但 50 行就能解决，重写。

问自己："一个资深工程师会觉得这过度复杂吗？"如果是，就简化。

## 3. 精准修改

**只改必须改的。只清理自己造成的混乱。**

编辑已有代码时：
- 不要"顺手优化"相邻的代码、注释或格式。
- 不要重构没坏的东西。
- 匹配已有代码风格，即使你自己有不同的写法。
- 如果注意到无关的冗余代码，提出来，但不要删。

当你自己的改动产生孤立代码时：
- 删除因你的改动而不再使用的 import / 变量 / 函数。
- 不要删除改动前就存在的冗余代码，除非被明确要求。

检验标准：每一行改动都应能直接追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "加个校验" -> "先为无效输入写测试，再让测试通过"
- "修这个 bug" -> "先写一个能复现 bug 的测试，再让测试通过"
- "重构 X" -> "确保重构前后测试都通过"

对于多步骤任务，先给出简要计划：

```
1. [步骤] -> 验证: [检查项]
2. [步骤] -> 验证: [检查项]
3. [步骤] -> 验证: [检查项]
```

强有力的成功标准让你可以独立循环推进。薄弱的成功标准（"把它搞能用"）则需要不断澄清。

## 5. 开发前需求确认

每次开发前必须完成以下步骤，缺一不可。

### 5.1 设计文档检查

- 确认是否有对应的设计文档（需求文档、技术方案文档、接口文档等）。
- 没有设计文档不开发。要求补充设计文档后再开始。

### 5.2 方案明确性审查

- 逐一审查方案中每个环节是否足够明确：
  - 输入/输出是否清晰定义
  - 边界条件是否覆盖
  - 与现有系统的交互方式是否明确
  - 异常场景是否有处理策略
- 发现不明确的点，列出问题清单，要求补充详细设计文档后再开始。

### 5.3 开发方案先行

- 正式编码前，先写出开发方案（计划）。方案内容包括：
  - 改动范围：涉及哪些文件、模块、接口
  - 实现步骤：按什么顺序做，每步做什么
  - 关键逻辑用**伪代码**表达，不要写详细实现代码
  - 验证方式：每步如何验证正确性
- 方案需评审通过后才能开始编码。
- 方案文档保存至 `docs/plan/` 目录（如 `docs/plan/xxx-plan.md`）。

**反模式：** 上来就写代码、边写边想方案、方案模糊就动手。

## 有效性标志

这些准则有效的标志是：diff 中不必要的改动减少，因过度设计而重写的情况减少，澄清性问题在实施前而非犯错后才提出。
