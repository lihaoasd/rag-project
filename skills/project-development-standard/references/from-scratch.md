# 从 0 构建项目要求

本文件用于“从 0 构建/新项目/新模块/新服务”任务。未完成设计确认前不写业务代码。

## 1. 需求文档与约束确认

- 必须建立需求文档，至少包含：目标用户、核心场景、功能范围、成功标准和验收方式。
- 明确边界：MVP 范围、不做的功能、性能/安全/合规约束。
- 确认技术栈、运行环境、已有系统、可复用依赖和部署方式。
- 多种理解全部列出；不确定处先问，不自行决定。

## 2. 技术文档与架构设计

- 必须建立技术文档，至少包含：技术栈、模块划分、数据流、存储、外部依赖、关键算法/流程、异常策略和部署方式。
- 必须明确项目结构：目录树、各目录职责、模块边界、命名约定；实现过程中保持结构与文档一致。
- 非 CRUD 业务必须补充业务详情文档，覆盖状态流转、业务规则、边界条件、权限、异常与一致性处理。
- 纯 CRUD 业务可轻量描述，但仍需明确实体、字段、接口、权限边界和基础校验规则。
- 有前端时，必须补充前端风格文档，覆盖视觉风格、组件约定、布局、交互、响应式和可访问性；优先写入 `docs/frontend/`。
- 文档放在项目既有文档目录；如无约定，按 [docs-classification.md](docs-classification.md) 的目录分类存放。
- 设计应满足：扩展点由真实需求驱动，模块边界清晰，核心逻辑与框架/IO 解耦。

## 3. 开发方案

- 在 `docs/plan/` 写方案，包含改动范围、实现顺序、关键伪代码、每步验证方式。
- 先搭可运行骨架与接口边界，再按纵向切片实现端到端功能。
- 方案评审通过后再编码。

## 4. 项目结构与实现

- 目录结构按职责组织，不按一次性页面/控制器堆叠。
- 分层清晰：表现层、应用层、领域/核心逻辑、基础设施层；允许根据项目规模简化。
- 先定义稳定接口再实现细节；内部实现可通过依赖注入/策略替换。
- 配置、常量、错误信息与业务逻辑分离；不做无必要抽象。
- 项目结构必须与 `docs/` 中定义的结构一致；新增目录或调整职责时同步更新技术文档。

## 5. 测试与验收

- 从 0 构建必须建立测试基础：单元测试、必要的集成测试、可运行验证命令。
- 核心业务规则至少覆盖正常路径、边界条件、非法输入和异常路径。
- 完成后运行全量相关测试和验收流程，更新 README/部署/接口文档。
- 每个阶段完成的修改都追加到修改记录；格式见 [change-record.md](change-record.md)。

## 反模式

- 没有需求文档直接生成代码。
- 先写完整业务代码，后补架构。
- 提前搭建大量配置、插件、抽象层。
- 目录、命名、接口没有一致性。
